# Lead Management code audit — 17 October 2026

The checklist is **not fully implemented**. Basic lead operations exist, but access-control defects, inconsistent status/conversion paths, incorrect reminder behavior and missing quotation workflows prevent a production-readiness sign-off.

Audit only: existing application code, configuration and database were not modified. This Markdown report is the only new artifact. Findings are static code findings; no lead was created, converted, deleted, or messaged during this audit.

## B. Critical findings and evidence

1. **P0 — Ordinary lead APIs do not isolate records or consistently authorize operations.** `routes/api.php:230` registers authenticated `/api/v1/leads` CRUD without per-operation permission middleware. `app/Http/Controllers/Api/LeadController.php:149` apiIndex queries leads without staff/owner scope; apiShow at 174, apiUpdate at 218 and apiDestroy at 290 load arbitrary IDs using findOrFail without policy checks. Authentication alone does not authorize access to that lead. A logged-in account can reach handlers for other users' records; no exploit request was executed.
2. **P0 — Management API status update bypasses record visibility.** `app/Http/Controllers/Api/V1/LeadManagementController.php:335` updateStatus resolves a source record directly. The shared request checks edit_leads but not ownership/assignment. The equivalent web handler at `app/Http/Controllers/Web/LeadManagementController.php:582` does call findNormalizedLeadOrFail. The API needs the same scoped lookup.
3. **P0 — Legacy web operations trust visibility instead of operation permissions.** `app/Http/Controllers/LeadController.php` store lacks create_leads authorization; findEditableLeadOrFail falls back to visible records without requiring edit_leads; destroy/deleteSelected/toggleStatus/export omit the corresponding operation guards. In `routes/web.php:307` these routes have the enclosing auth gate only. A hidden create/delete button is not a backend permission.
4. **P0 — Conversion can change an existing staff/admin account's raw role.** `app/Services/LeadManagement/LeadClientConversionService.php:13` ensureClientFromLead finds any user by email and sets role=client when role is not client. A lead matching an employee/admin email can modify that account. Spatie role pivots are not reconciled, so raw-role and permission state can diverge. Reject non-client collisions rather than mutating roles.
5. **P0 — Predictable password in legacy conversion.** `app/Http/Controllers/LeadController.php:135` and `app/Http/Controllers/Api/LeadController.php:254` create clients with Hash::make('123456789'). The main conversion service uses a random password, but legacy edit conversion remains exposed. Use a verified invitation/reset flow and assess previously created accounts.
6. **P0 — Reports disclose global data.** Both performanceStats implementations require only management-view access, then query all Lead/LeadFollowup/StaffLeadStat records. Scoped list visibility is not applied. Any permitted management viewer can obtain unrelated totals and staff performance.
7. **P0 — Private notes have no reader isolation.** Web show at line 162 and API show/listNotes retrieve all notes. AddLeadNoteRequest persists is_private, but queries do not restrict private notes by author or privileged role.
8. **P1 — Multiple state-machine bypasses.** Dedicated status PATCH calls UpdateLeadStatusAction -> LeadStatusService. In contrast, addFollowup assigns status directly, accepts any max-50 string, does not require lost_reason, and does not create the customer on converted. Legacy create/update/toggle also skip transitions/history/auto-actions. Dedicated validateTransition also checks target lost/junk before checking closed source; converted -> lost can pass while conversion/customer data remains unchanged.
9. **P1 — Unsafe pipeline identity resolution and read side effects.** Both resolveLeadEntityForPipeline implementations match any lead by email OR phone without source/owner scope. If both are blank/'-', neither where is applied and first() selects an arbitrary lead. Status update passes a reduced payload; bulk assignment passes null contact fields, which can trigger this case. Profile/history GETs invoke the same resolver and may create a mirror. Contacts shared by unrelated leads can combine histories, assignments, private notes and conversion identities. A stable unique source_type/source_id mapping is required.
10. **P1 — Reassignment retains previous staff.** Main assign/bulkAssign merge old IDs with selected IDs. There is no remove/revoke action. LeadPipelineService.assignLead logs only the first staff ID as the active primary assignment although multiple staff retain access. Legacy edit replaces IDs but skips matching assignment history/notifications.
11. **P1 — Conversion is not idempotent or consistent.** Dedicated convertLead creates a LeadConversion every request, accepts client_id as any integer without exists/client-role/visibility checks, bypasses the transition service and does not update the original external source's status. The status action uses updateOrCreate and syncs the source. Legacy update writes lead changes in a transaction but creates client/address/business data afterward, with no conversion record/history. API buildLeadPayload also overwrites created_by during update.
12. **P1 — Manual and proposal reminders have no delivery dispatcher.** LeadPipelineService.createReminder inserts/logs only; no due-reminder scanner or dispatch call was found for these pending rows. Proposal status auto-action also inserts only. Calendar display is not delivery.
13. **P1 — Delayed reminders are immediate in the supplied local configuration.** Only the non-secret QUEUE_CONNECTION setting was inspected: .env sets sync. The installed framework's vendor/laravel/framework/src/Illuminate/Queue/SyncQueue.php later() immediately calls push(), ignoring delay. Followup day-before/15-minute jobs therefore run in the request instead of waiting, assuming this env value is effective; cached runtime configuration was not inspected. In addition, contacted creates a reminder due next day but dispatches at now+1 minute even with an asynchronous queue.
14. **P1 — Delivery records falsely claim success.** SendLeadEmailReminderJob and SendLeadWhatsappReminderJob contain provider placeholder comments and only mark sent. SendLeadDashboardReminderJob ignores UnifiedNotificationService.sendToUser()'s success/failure return and marks sent regardless. Adjacent Meta welcome WhatsApp has real provider handling/tests; this does not make the separate followup reminder jobs complete.
15. **P1 — Reporting math and stale materialized stats.** Web/API monthlyWonLeads/monthlyLostLeads filter whereYear(updated_at), yielding year totals labeled monthly. pendingFollowups counts due/overdue leads and can include closed leads. Lost includes junk in one KPI and excludes it in another. StaffLeadStat is initialized/read, but no ongoing live updater was found; StaffLeadAnalyticsService already calculates useful live metrics and should be reused.
16. **P2 — Scale and consistency risks.** mergedLeads loads full tables, then resolves assignees and access with per-row queries, then filters/sorts in PHP and sends all matching rows plus modal HTML to DataTables. findNormalizedLeadOrFail repeats this for single-record actions. Pipeline tables have useful indexes but lack FK constraints; conversion rows lack a unique lead guard. Bulk assignment can partially commit because there is no encompassing transaction.

## G. Final assessment and limits

**Not ready for a full business-production sign-off against this checklist.** The module can serve as a basic lead list and manual activity tracker, but permission bypasses and customer/conversion identity defects must be fixed before broad sales-team use. Reminder timing/delivery, reassignment, conversion consistency and report correctness are essential next repairs.

A complete sales lifecycle is not implemented: quotation is a label rather than an entity, and customer conversion does not create a project/order. Existing functions provide a useful base and should be repaired incrementally.

Runtime items remain Not Verified: live schema alignment, actual deployed roles, browser interactions, provider delivery, effective cached queue settings, cron/worker operation and measured test coverage. The supplied SQL dump confirms schema definitions but is not proof of the currently imported database. No claim is made that static findings were reproduced through live destructive requests.

Await approval for implementation; this audit creates only this report and makes no application/configuration/database changes.
